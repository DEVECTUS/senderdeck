# Organic social publishing

Version 0.4.37 adds five independent destinations: Instagram feed, Facebook Page feed, LinkedIn company feed, Instagram Story and Facebook Story. This does not enable customer replies, renew WhatsApp test allowances, expand scopes or install a daily scheduler.

## Authority and setup

The brand owner/admin records existing standing authority with policy_preview and policy_set, binding each channel to its exact account and provider asset. Explicit null accounts permit planning only the exact unconnected asset. Save revision 0 initially, or the current policy revision when changing it. RoutineOnly must be true, paidPromotion false, timezone Australia/Sydney. Saving requires the exact preview confirmation. Cancelling, declining, holding, disabling or changing the policy blocks unstarted writes. Policy-author membership is checked again at dispatch.

Hosting SOCIAL_PUBLISH_ENABLED must explicitly equal true before any public write. Deployment alone leaves this off. Existing SOCIAL_SEND_ENABLED, WhatsApp allowance, inbox validation, monitoring and reply approvals are independent. No production account or policy is created by migration.

Meta needs an app-bound live user grant, exact destination discovery and current CREATE_CONTENT or MANAGE Page task. Facebook publishing requires pages_manage_posts, pages_read_engagement and pages_show_list. Instagram requires instagram_basic, instagram_content_publish, pages_read_engagement and pages_show_list. Story publishing additionally verifies Instagram account_type BUSINESS. App review, advanced access and granting consent remain actual provider requirements; deployment does not request consent or change current scopes. The explicit owner publishing-connection action can request the required scope upgrade only through Meta consent. A missing scope is a provider setup blocker, not stale client discovery.

In Publishing, choose the exact brand, expand Owner publishing connection under the exact existing Facebook/Instagram destination, and choose Authorize this account for its channel only with separate consent authority. The server uses META_PUBLISH_LOGIN_CONFIG_ID when set, otherwise META_LOGIN_CONFIG_ID. This must be a Facebook Login for Business user-token configuration permitting the displayed required permissions; the actual Meta consent screen remains authoritative. Stop if it asks for unrelated new access. Register callback /oauth/social/publishing/meta/callback on the existing public origin. After consent, choose Inspect returned publishing access, review the exact account and permissions, then Save this exact account connection. The new grant must retain existing scopes, use the same granting identity, verify exact asset/task and pass live publishing checks. Saving replaces only that account credential; other account records, inbox validation evidence and reply policy are preserved, while inbox freshness is invalidated for a later read recheck. Missing scopes after consent preserve the original credential. The supporting tools are social_publish_meta_start, meta_inspect and meta_complete. A missing approved permission or misconfigured provider configuration must be corrected by the platform owner in Meta; this release does not make provider changes.

LinkedIn requires LINKEDIN_CLIENT_ID and LINKEDIN_CLIENT_SECRET, LINKEDIN_COMMUNITY_APPROVED=true only for a genuinely approved configured Community Management app, and optionally LINKEDIN_API_VERSION (default 202608). Register the exact public-origin /oauth/social/linkedin/callback. Organization access requires r_organization_admin, r_organization_social and w_organization_social, live 3-legged token introspection and an exact approved organization admin/content role. OAuth is a separate explicit owner action. Selection is user/brand bound, expires after ten minutes and cannot reassign another brand's organization. It enables company publishing only, not LinkedIn inbox access. Do not fabricate app approval or use a browser login as an API credential.

## Daily workflow

1. Discover the brand and actual accounts, then call social_publish_capabilities. Read the policy and save it only within explicit standing owner authority.
2. Import actual historical receipts before preparing a current topic. Import never publishes. Provide the exact local account or explicit null, asset, channel, actual publication time, actual provider ID or URL and positive observation evidence. Unknown Story expiry is null. Historical expired Stories remain published.
3. Upload each approved image with media_prepare (JPEG/PNG, 4 MiB maximum, SHA256), media_chunk (32 KiB decoded per chunk) and media_complete. Local PNG-to-JPEG conversion for Instagram must preserve dimensions and content; record the original sourceSha256. Other platforms can retain PNG. Media is encrypted, expires after at most two days and is exposed to provider fetch only via an opaque expiring signed URL. Provider-fetch URLs are never returned in tools. No arbitrary source URL fetching is supported.
4. social_publish_prepare accepts contentKey, topicDate, title and 1 to 5 independent targets: channel, exact accountId or null, assetId, approved caption, altText and mediaId. Story caption is empty; approved text must be in the separate 9:16 image. No automatic cropping, music, stickers or new links. Feed alt text is submitted and verified only if actual readback supports it. Story alt text is not supported. One brand/date and brand/contentKey are unique. Unfinished targets can be revised with the inspected revision, preserving delivered targets exactly; active or unknown attempts block revision.
5. Inspect the current item and digest. Validate each destination, then preflight. These are separate from inbox freshness. Duplicate scans are bounded and must be exhausted; existing same-day content blocks publication. LinkedIn's published-post scan does not expose native planner scheduling. Incomplete or unsupported schedule coverage requires an actual native published/scheduled/active-Story inspection, then admin clearance_record with observedAt within five minutes and concrete evidence. This cannot override grants, known receipts or uncertain outcomes.
6. Release each destination with itemId, channel and current digest, or call due for this exact brand. Today's Sydney date at/after 09:00 only; no backfill. Each Story requires this topic's corresponding feed receipt. The caller's existing authorized daily task supplies scheduling. This service does not create an automation.
7. Record each independent provider readback receipt. 201 plus LinkedIn x-restli-id is a valid create response with no JSON body; the service then verifies the exact company post. A missing permalink stays null. Unexposed Story expiry stays null. A rejected destination does not stop independent feeds or the other verified feed's Story.
8. Unknown delivery locks retry. Known provider IDs use reconcile (read-only provider requests); lost IDs require positive native receipt import. Never reset an unknown row or republish to test connectivity. A later failed read cannot erase a published receipt. Stale in-flight attempts require reconciliation. Cancellation cannot retract an already dispatched network request.

## Tools and client discovery

All 25 social_publish_* tools are advertised through /api/mcp tools/list; calls authenticate with senderdeck OAuth scope, strict schemas and read/write annotations. The browser management path is Publishing in the main navigation. It shows independent capability blockers and receipts, access checks, duplicate checks, approved per-destination release, reconciliation, owner hold/cancel/decline and separately authorized LinkedIn connection. Upload and approved-policy preparation use the tools above. If server discovery includes the tools but a connected client omits them, refresh client discovery without disconnecting or expanding credentials.

The existing customer reply flow still requires exact draft revision approval. A publishing policy is never reply approval.

## Storage, maintenance and rollback

Apply additive migration 0012_social_publishing.sql before deploying source. Six new tables store encrypted policy/manifest/media, delivery receipts and fresh validation/clearance. Brand/customer removal cascades new records; account disconnection preserves the delivery receipt with null account association. Expired media and checks are removed by existing maintenance. Ordinary items follow brand retention; unresolved publishing/unknown items are retained for reconciliation rather than losing duplicate locks, and remain inspectable after expiry. Resolve these explicitly before routine retention cleanup. No provider content is deleted by cleanup.

Rollback: disable SOCIAL_PUBLISH_ENABLED first and preserve D1 records, then redeploy saved v0.4.36. Do not down-migrate or delete the new tables while there are in-flight/unknown outcomes. The old application does not know the new delivery ledger: pause its daily publishing callers during rollback and do not retry unknown posts outside this service. Existing source, audience, scheduler settings, reply flags and WhatsApp expiry remain unchanged.

## Verification limits

Tests use complete provider fetch interception and synthetic assets. They verify five separate receipts, alt-text honesty, 201/header handling, scope isolation, concurrency, partial revisions, cancellation, native history, bounded scans, unknown locks, read-only reconciliation, media expiry/signature and actual MCP discovery. No real test post or provider consent is performed. Production readiness still requires real provider scopes, app approval and exact destination checks. The current Car Turntable connection lacks publishing scopes and has no configured LinkedIn organization grant; deployment cannot resolve those provider barriers by itself.
